  1. O que acontece quando uma exceção é identificada

  A execução não para. A exceção segue um de três caminhos, nesta ordem de
  precedência:

  1. Já existe decisão humana para ela (em config/decisoes.yaml, achada pela
     chave, que é tipo + ref_origem). O sistema aplica a decisão com
     metodo=HUMANO e segue.
  2. Existe agente para esse tipo de exceção. O agente propõe uma resposta. Se
     ela passa no guardrail e na confiança mínima, é aplicada com metodo=IA.
     Caso contrário, vai para o caminho 3.
  3. Nenhum dos dois. A linha entra em pendencias.csv e em fila_humana.csv, com
     o motivo, a pergunta e quem decide.

  Quando cai no caminho 3, o sistema não deixa o número em branco nem chuta. Ele
  aplica o tratamento seguro (o que o PRD chama de "default"). Exemplo: o PIX
  de R$ 18.240 sem operação é classificado na conta provisória 2.1.02.001,
  aparece como pendência e fica fora de qualquer nota ou comissão. A saída sai
  completa, com esse item marcado como "aguardando decisão".

  A exceção a isso são erros estruturais: layout de arquivo inesperado, cadeia
  de saldos da Aurora que não fecha, invariante de rastro que falha. Esses
  abortam a execução com mensagem clara.

  2. Regra não definida, ou que mudou

  Para o sistema, "regra não definida" e "regra mudou" são o mesmo evento. Ele
  só vê que os dados não se encaixam no que está configurado e abre uma exceção.
  Por exemplo:

  - A Casa do Estudante volta a ter taxa em janeiro. Nenhuma regra cobre isso, e
    o resolvedor de taxa devolve CONTRATO_AMBIGUO ou aplica o override vencido.
  - Aparece um lojista ou EC novo, e sai ENTIDADE_NAO_RESOLVIDA.
  - Aparece um tipo de lançamento sem padrão, e o Classificador é chamado.

  Quem informa é o financeiro, respondendo a fila_humana.csv com uma linha em
  decisoes.yaml:

  - chave: PEN-LANCAMENTO_SEM_ORIGEM-MRD2026090425
    decisao: {conta_codigo: "2.1.02.001"}
    decidido_por: Helena
    data: 2026-10-18
    escopo: caso      # ou "regra"

  Se for mudança de contrato já conhecida (por exemplo, "Bridge renegocia em
  15/09"), o caminho é alterar config/regras.yaml com a vigência. Não é uma
  decisão por caso.

  3. Como a regra entra no processamento determinístico

  O campo escopo decide:

  ┌────────┬───────────────┬────────────────────────────────────────────────┐
  │ Escopo │  O que vale   │            Como vira determinístico            │
  ├────────┼───────────────┼────────────────────────────────────────────────┤
  │ caso   │ Só aquela     │ Não vira. Fica em decisoes.yaml e é reaplicada │
  │        │ linha         │  nas rodadas seguintes.                        │
  ├────────┼───────────────┼────────────────────────────────────────────────┤
  │        │ Todos os      │ python -m tarvo promover <chave> grava a regra │
  │ regra  │ casos do      │  em config/*.yaml. A partir daí, o motor       │
  │        │ mesmo padrão  │ resolve sem agente e sem humano.               │
  └────────┴───────────────┴────────────────────────────────────────────────┘

  Regra promovida passa a gerar regra_id no rastro, então dá para auditar qual
  regra produziu cada número. A precedência fica: decisão humana > regra em
  config > agente > pendência.

  A lacuna que o PRD não cobre

  A promoção só funciona para regras que cabem num schema de config que o código
  já sabe ler. Hoje são cinco:

  - padrão de descrição → conta
  - override de taxa com vigência
  - alias ou EC de lojista
  - quem_decide por tipo
  - flags e tolerâncias

  Uma regra de cálculo nova (por exemplo, "antecipação passa a ter piso mínimo")
  não entra por YAML. Ela exige código e teste. O sistema deve tratar isso como
  exceção permanente: o item fica pendente, com o tratamento seguro, até alguém
  implementar.

  O PRD também assume que o financeiro edita YAML, o que é irreal. Eu trocaria
  decisoes.yaml por uma planilha ou CSV de respostas, com colunas chave,
  decisao, escopo, que o sistema lê e valida.

  exceção, a tabela dos tipos de regra promovíveis e o formato da planilha de
